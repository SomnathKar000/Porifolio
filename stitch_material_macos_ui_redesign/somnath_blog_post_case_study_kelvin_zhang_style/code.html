Distributed Asset Pipeline & Storage Architecture

Background

As traffic and media ingress scaled across our core services, traditional HTTP multi-part proxy uploads began causing severe bottlenecking across our internal compute clusters. Application containers spent an exorbitant percentage of their active event loop processing incoming byte streams, locking valuable thread pools merely passing binary payloads to cloud storage.

We engineered Vortex, an end-to-end distributed ingress system relying on client-orchestrated pre-signed multi-part authorization. The architecture eliminated 35% of ingress server network utilization overnight and established an idempotent upload model capable of surviving erratic mobile connections and high concurrency spikes.

Our core engineering requirements were:

  • Zero server throughput bottlenecks by delegating data payloads directly to AWS S3 storage edge tiers.
  • Guaranteed idempotency via cryptographic SHA-256 preflight checks and distributed Redis locks.
  • Strict telemetry consistency ensuring synchronous validation through event-driven webhooks and stateful cleanup jobs.

Principles

Resilience

In distributed client environments, intermittent connectivity is an inevitable default. Every single endpoint within our ingest API is rigorously idempotent. If an upload chunk drops halfway through transmission, the client can query our storage orchestrator and resume specifically at the missing byte boundary without re-uploading completed segments.

Zero Bottleneck Proxy

Standard proxying through server compute instances introduces dual hops and unneeded latency. By isolating the API server's responsibility purely to credential negotiation, we leverage AWS S3’s native scalability. Edge nodes sign short-lived STS tokens in under 15ms, leaving our compute cluster entirely unburdened by heavy bandwidth transfers.

Deterministic State

An asset is never assumed complete until an asynchronous checksum verification cycle passes. Real-time S3 bucket notifications publish metadata events into a message queue, triggering automated virus evaluation, dimension extraction, and database state transitions without holding client connections open.

Presigned Multi-Part Generation

The pipeline hinges on our session initialization worker. When an upload session initiates, the API hashes the object key with customer workspace scope and generates chunked upload parts in parallel: 

export async function createPresignedSession(
  fileHash: string,
  totalParts: number,
  userId: string
): Promise<UploadSession> {
  // Acquire Redis atomic lock to prevent dual initialization
  const acquired = await redis.set(`lock:upload:${fileHash}`, userId, 'NX', 'EX', 60);
  if (!acquired) throw new ConflictError('Upload already in progress');

  const multiPart = await s3.createMultipartUpload({
    Bucket: env.STORAGE_BUCKET,
    Key: `raw/${userId}/${fileHash}`
  });

  const parts = await Promise.all(
    Array.from({ length: totalParts }, (_, i) =>
      s3.getSignedUrlPromise('uploadPart', {
        Bucket: env.STORAGE_BUCKET,
        Key: `raw/${userId}/${fileHash}`,
        PartNumber: i + 1,
        UploadId: multiPart.UploadId,
        Expires: 900 // 15 minutes
      })
    )
  );

  return { uploadId: multiPart.UploadId, signedUrls: parts };
}
